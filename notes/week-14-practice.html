WEEK 14 / 2026-12-07 / MONDAY 14:00-17:00

Enforce bounded execution; test authorization and failures; bind simulated approvals to exact actions.

State, budgets, and trust boundaries

An agent is a controlled loop

An action proposal must pass the harness before changing the environment.

Worked reasoning: State; transition; attempt budget; tool permissions; tool errors; approvals; trace evidence.

Where does the model lose authority?

At every deterministic gate. A proposal cannot change the action set or enlarge its own budget.

Workflow and agent are not synonyms

A fixed graph is a workflow; model-directed choices add an agent decision layer.

Worked reasoning: A three-step measurement report can use a script. Do not add open-ended planning when the steps are known.

Does a loop alone make a system an LLM agent?

No. The core notebook is a deterministic harness simulator. The language-model decision component is deliberately absent.

Represent state before writing actions

State records attempts, observations, pending approval and terminal status.

Worked reasoning: After budget_exhausted, later proposals must not execute. A terminal status is not just a displayed message.

What is the invariant after stopping?

The executed action count and side-effect log do not change. Tests should attempt an additional action.

Budgets need an accounting unit

Count attempts, tool calls and declared work separately.

Worked reasoning: Three invalid proposals under a two-attempt cap must stop at the cap even though no tool ran.

Can a tool-call cap guarantee short runtime?

No. One call may hang or be expensive. Wall-clock limits and resource isolation are distinct controls.

Validate before dispatch

Unknown tool names must not reach an implementation or external service.

Worked reasoning: Compare a permitted mean request with a fake send_email request. The simulator sends no real message.

What must the trace prove about the forbidden request?

It was rejected before dispatch; do not rely on a downstream tool happening to fail.

Use typed errors with narrow recovery

Invalid input, transient tool failure and permission failure need different next steps.

Worked reasoning: A bounded retry can handle a simulated transient error; it cannot authorize a forbidden operation.

Why can retries make behavior worse?

Repeated side effects, cost and duplicate operations may occur. Retry only a declared safe operation with a bound.

Untrusted text cannot amend policy

Retrieved instructions are data even if they imitate a system message.

Worked reasoning: Store the fixture text and show that the allowed tools remain unchanged after it is observed.

Does this test prove universal prompt-injection resistance?

No. It tests one deterministic boundary and supplied cases; real model-mediated paths require broader adversarial evaluation.

Approval must name the exact action

Bind action, arguments and a unique nonce into a reviewed digest.

Worked reasoning: An approval for draft A cannot be reused for draft B with different content or destination.

Why is an 'approved=true' field insufficient?

Untrusted callers could set it themselves. Approval must come from a separate authority and be checked against the exact request.

Consumption prevents approval replay

A valid approval is one-use and has a declared expiration rule.

Worked reasoning: The first simulated action can succeed; the second must be rejected without a duplicate event.

What limitation remains in this teaching approval?

It models a local trusted registry, not distributed identity, cryptographic authentication, real messaging or production security.

Summary: make unsafe transitions impossible

Place gates in code rather than hoping a model follows instructions.

Worked reasoning: Show why a retrieved sentence cannot reach the simulated send action without a separately approved digest.

What will the next hour measure?

Expected versus actual behavior for each boundary, including errors, stops and approval misuse.

Failure cases and human approval tests

A safety claim needs a negative test

A normal success case does not probe a forbidden transition.

Worked reasoning: Each row states initial state, proposal, expected status and permitted side effects.

Why not use only example conversations?

They may omit the actual execution boundary. Test the harness state and side-effect log directly.

Test status and side effects together

A rejection message is insufficient if the operation already happened.

Worked reasoning: A function can append an event and then return rejected. Checking only the string would miss the violation.

Which assertion detects that bug?

Assert that the event count and protected state are unchanged for every rejected action.

Task 4: probe schema edge cases

Boolean, NaN, empty values and unknown fields should fail explicitly.

Worked reasoning: A separate case reveals which check was skipped when a regression occurs.

Does rejecting all requests make a good agent?

No. Include legitimate requests to measure functionality alongside safety. Always rejecting can pass a narrow negative-only suite.

Task 5: exhaust the attempt cap

Use a plan longer than the cap and inspect the exact stop index.

Worked reasoning: The simulator records two consumed attempts at cap two; a later proposal returns stopped.

Why test after the stop?

It verifies terminal-state enforcement rather than merely detecting that a stop message once appeared.

Task 6: bind approval to arguments

Change one field after approval and verify digest mismatch.

Worked reasoning: Wrong nonce, expired approval and already-consumed approval are distinct rejection cases.

Can a digest prove who approved it?

No. It detects request mismatch relative to a trusted approval record. Identity assurance is outside this local simulator.

Simulated timeout is not process isolation

A fake slow-step flag exercises an error branch, not operating-system enforcement.

Worked reasoning: The notebook has no blocking network tool. A production tool requires real timeout and cancellation controls.

Why avoid claiming runtime security here?

An in-process check cannot forcibly stop arbitrary blocking code. The demonstration only tests control-flow handling.

Retry only a declared transient failure

A bounded retry preserves the original request and logs each attempt.

Worked reasoning: Timeout may be retryable for a read; permission_denied is never repaired by repeated calls.

What if a request has a side effect?

A retry can duplicate it. Use idempotency keys or transactional semantics, not blind re-execution.

Audit traces are bounded evidence

Record events without secrets, irrelevant personal data or fabricated reasoning.

Worked reasoning: Identify the first failed precondition and show that later protected events are absent.

Does a trace prove the implementation was not bypassed?

Not by itself. Tests, provenance and independent observation of the execution boundary are also needed.

Human review must offer a real choice

Show exact action, evidence and consequences before approval.

Worked reasoning: Name recipient, content, reason and whether the operation is reversible. Our notebook uses local fictional destinations only.

Why is vague confirmation weak?

A user cannot meaningfully authorize an unspecified or changed operation. Review scope must match execution scope.

Summary: safety and usefulness are separate

Report legitimate success and forbidden-action violations with denominators.

Worked reasoning: Save per-case expected/observed statuses and event counts, not just 'all passed'.

What does zero observed violations mean?

No violation was observed in this finite suite. It is not a universal guarantee of safe deployment.

Oversight studio: attack the boundary

Probe the harness without real side effects

All destructive, messaging and approval operations remain simulated.

Worked reasoning: Restore 5 min; core tests 25 min; approval review 15 min; peer audit and export 15 min.

What is not being tested?

Real identity services, real mail APIs, operating-system sandboxes and a live language model.

Task 1: accept a legitimate operation

Verify the permitted mean and its independent expected value.

Worked reasoning: A dispatcher that rejects every proposal is not a useful reference even if it never performs a forbidden action.

Which denominator belongs to legitimate success?

The number of valid requests in the declared suite, not all requests including deliberate attacks.

Task 2: keep malicious text powerless

Pass the injection fixture as content, never as executable instructions.

Worked reasoning: The allowed-tool tuple and approval registry must not be modified by retrieved prose.

What would invalidate the test?

Changing the contract in the test to make the attack pass or executing a parsed instruction from the hostile text.

Task 3: prove one-use approval

Inspect the digest and event count after the first use and replay.

Worked reasoning: A replay test needs the same registry. A fresh registry would represent a different authorization context.

Why does this matter for reproducibility?

Stateful security behavior depends on event order. Preserve initial state and the exact sequence of requests.

Task 4: differentiate malformed inputs

Name the failing precondition for each deliberately invalid proposal.

Worked reasoning: For True, explain numeric subtype confusion; for NaN, explain nonfinite arithmetic and JSON portability.

Why not catch every exception and return success?

It would erase the failure semantics and could hide partial execution or implementation errors.

Task 5: inspect the terminal state

After cap exhaustion, compare the complete action log before and after.

Worked reasoning: Reset only by an explicit new session with a fresh state record and a new evidence ID.

When is a reset legitimate?

When declared as a new run, not as an invisible way to exceed the budget of an ongoing task.

Task 6: modify an approved request

Change one argument without issuing a new approval.

Worked reasoning: A partner should see exactly which field changed and why the original approval no longer matches.

Could the caller approve its own changed request?

Not under this contract. Approval creation is a separate trusted teaching action, not an allowed model tool.

Task 7: reconstruct the first failure

Follow the trace from proposal to rejection to stop.

Worked reasoning: Explain the observed predicate and result. Avoid inventing what a model internally thought.

What is a defensible explanation?

A mechanism tied to code, inputs and trace events with a stated boundary on what was observed.

Task 8: preserve a negative result

Export a case that fails as expected and one valid success.

Worked reasoning: The expected error must be caught by the test, not hidden by removing assertions.

When does an expected rejection become a defect?

When a valid request is rejected or an invalid request causes an unauthorized side effect.

Summary: extend one threat model at a time

Optional A adds a bounded retry; optional B alters one approved argument.

Worked reasoning: Name a real-world boundary that the local simulator cannot establish and propose a suitable next test.

What connects to Studio I?

The workflow will combine retrieval and numerical evidence while preserving these same permission and stop boundaries.
