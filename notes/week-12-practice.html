From next-token prediction to tool proposals

Language is an interface, not an oracle

Generate a proposal, then verify the claim outside the model.

Worked reasoning: Token probabilities; sampling; structured proposals; validation; Task 1 prediction.

What could make fluent output incorrect?

A likely token sequence can lack factual evidence, correct arithmetic, or permission. Separate these checks.

A token is not necessarily a word

A tokenizer maps text to integer IDs using a specified vocabulary.

Worked reasoning: Character demo: hot = h,o,t; a production subword tokenizer can split differently. Preserve tokenizer identity.

Can one word always be counted as one token?

No. Token boundaries depend on the tokenizer and text. The notebook uses characters, not a production LLM tokenizer.

Autoregression factorizes a sequence

Each conditional distribution uses the preceding context only.

Worked reasoning: p(A)=0.5; p(B given A)=0.6; p(C given AB)=0.2; joint probability=0.06.

Does the factorization prove the sequence is true?

No. It describes sequence probability under a model, not truth. The multiplication follows the chain rule.

Cross-entropy penalizes surprise

Training lowers negative log probability on observed next tokens.

Worked reasoning: If p=0.8 then -ln(p)=0.223; if p=0.2 then loss=1.609. Mean=0.916 nats.

Why is assigning low probability to the observed token costly?

Negative log grows as probability approaches zero. Mean teacher-forced loss is not factual verification.

Attention selects context-dependent mixtures

Causal masking prevents a position from reading later tokens.

Worked reasoning: At position 2, keys 1 and 2 are allowed; keys 3 and 4 are blocked before softmax.

Does attention provide an external source of facts?

No. It mixes representations from supplied context. Retrieved evidence and its quality remain separate responsibilities.

Pretraining and post-training differ

Pretraining learns broad prediction; post-training changes response behavior.

Worked reasoning: A polite response with well-formed JSON can contain an incorrect number or an unsupported citation.

Does instruction tuning remove the need for tests?

No. Behavior adaptation is not a guarantee of accuracy, authorization, or grounding.

Sampling changes a distribution

Temperature divides logits before softmax; it is not a truth control.

Worked reasoning: Logits [2,0]: T=1 gives [0.881,0.119]; T=2 gives [0.731,0.269].

What does increasing temperature change here?

It flattens this distribution and raises the lower-logit token probability. It does not make the content more or less factual by definition.

A tiny language model is inspectable

Character bigrams estimate the next character from one previous character.

Worked reasoning: Run the fixed original teaching corpus. Find the most frequent successor of a space and compare its count with its probability.

Is this a miniature Transformer?

No. It is a trained conditional-count language model with one-character context; it lacks attention and contextual embeddings.

Prediction before sampling creates evidence

Keep corpus, vocabulary, smoothing and random seed with the generated text.

Worked reasoning: Predict whether lower temperature concentrates probabilities; compare entropy and sampled continuations without changing the corpus.

Must a lower-entropy model produce a better answer?

No. Entropy measures distribution concentration. Quality needs a task-specific evaluation independent of sampling sharpness.

Summary: separate probability and proof

A language model proposes tokens; verified tools establish bounded numeric results.

Worked reasoning: Show one next-character distribution, one computed loss and one limitation of the bigram model.

Which component will authorize the next tool call?

Deterministic validation outside the model. A model probability cannot grant permission.

Structured outputs and bounded tool execution

The tool boundary is executable code

A proposal becomes an action only after deterministic validation.

Worked reasoning: Tasks 3-5: valid JSON, invalid JSON, tool allowlist, numeric checks and a finite attempt budget.

Why not execute a plausible tool name directly?

A tool name is untrusted data. Unknown names must be rejected without dynamic evaluation or dispatch to arbitrary code.

JSON syntax is only the first gate

Successful parsing establishes a data structure, not its meaning.

Worked reasoning: Allowed: tool=mean with finite values. Not allowed: tool=delete_files even when the JSON parses.

Can a structured-output guarantee replace permissions?

No. Syntax, schema conformance, semantics and authorization are distinct guarantees.

Use exact fields and explicit types

Reject booleans, NaN, empty arrays and oversized arrays before calculation.

Worked reasoning: In Python isinstance(True,int) is true; the validator uses type(x) in (int,float) and a finite check.

Why reject a Boolean in numeric readings?

Its programming-language subtype does not establish the intended measurement meaning. The declared contract accepts numeric readings only.

No natural-language sentence grants tools

A retrieved instruction remains content, even when it looks urgent.

Worked reasoning: Try delete_files and a values array containing 'ignore rules'. Verify no external side effect occurs.

What is the enforcement point?

The allowlist and schema validator, not a promise in the system prompt. These probes cover only the supplied implementation and cases.

Numerical results need their own checks

Valid inputs can still overflow a calculation; validate the result too.

Worked reasoning: Test the bounded mean implementation with large finite inputs; it must return a finite result or an explicit rejection.

Does a valid schema prove the arithmetic is correct?

No. Independently check arithmetic against small fixtures and reject nonfinite outputs rather than silently serializing them.

A finite budget belongs to the harness

Count attempts before dispatch; rejected proposals still consume an attempt.

Worked reasoning: Submit three proposals. The third must be budget_exhausted and must not invoke a tool.

Why count rejected attempts?

Otherwise repeated invalid proposals can loop forever without spending the nominal tool budget.

Trace observable events, not hidden thoughts

Store proposal, validation status, output and stop reason.

Worked reasoning: Locate the proposal that failed and the code that blocked it. A trace is an observable execution record, not private chain-of-thought.

Can a detailed trace establish truth by itself?

No. A trace improves inspection; incorrect code can log incorrect results consistently.

An LLM adapter is optional, not required

Manual or captured JSON proposals exercise the same boundary at zero inference cost.

Worked reasoning: Use a well-formed and a malformed response. Record parse success, validation success and numeric correctness separately.

Are we evaluating a real LLM in the core notebook?

No. It trains a small count model and uses explicit tool proposals. Optional external outputs must be labeled with model and date and evaluated separately.

Vibe coding needs acceptance criteria

Ask for a small change with inputs, forbidden behavior and tests.

Worked reasoning: Add median as an allowed tool; preserve mean behavior; reject unknown tools; add odd/even/empty cases.

Why is 'make this agent smarter' insufficient?

It does not specify observable behavior or a stopping condition. Students must review actual code and preserve the reference behavior.

Summary: the model never owns permissions

Parsing, validation, execution and recording are separate stages.

Worked reasoning: Save a valid result, a rejection and a budget stop. Keep the original proposal alongside each event.

What evidence must survive the runtime?

Inputs, contract, source, versions, trace and exported results. A successful chat screenshot is insufficient.

Tool-contract studio: test, explain, export

Build a proposal-to-evidence artifact

Finish eight core tasks before attempting optional changes.

Worked reasoning: Restore 5 min; core tasks 25 min; peer checks 20 min; export and exit 10 min.

What do you restore after a runtime reset?

Run the notebook top to bottom; do not paste a remembered result into an evidence record.

Task 1: read a learned distribution

Compare successor counts with add-one probabilities for one context character.

Worked reasoning: With vocabulary size V and context count N, add-one assigns 1/(N+V) to an unseen successor.

What did smoothing assume?

A symmetric pseudo-count over the vocabulary. It avoids zero probability but is not evidence that the successor was observed.

Task 2: compare sampling controls

Record entropy for the same logits at two positive temperatures.

Worked reasoning: Use a fixed seed per run and preserve the probability vectors, not just the sampled strings.

Can two different temperatures produce the same short string?

Yes. One sampled continuation is a noisy observation and does not identify the underlying distribution.

Task 3: reject the unknown capability

Send an unknown tool name to the same dispatcher.

Worked reasoning: Record expected status before calling the dispatcher. Verify that no accepted result is produced.

Should the validator silently rename an unknown tool?

No. Silent repair changes the requested operation. Return a specific failure and require an explicit new proposal.

Task 4: classify malformed readings

Test empty, Boolean, string, NaN and infinite values separately.

Worked reasoning: The JSON parser rejects nonstandard constants; numeric validation also rejects nonfinite native Python values.

Why keep separate tests for text and Python objects?

They enter through different boundaries. Passing one path does not prove the other path uses the same checks.

Task 5: stop a repeated proposal loop

A cap counts every attempt, not only successful actions.

Worked reasoning: A cap of two permits at most two validations/dispatch attempts; the third event records a budget stop.

What would happen if only successes counted?

A sequence of malformed proposals could make no progress indefinitely while never reaching the cap.

Task 6: repair syntax without changing intent

Correct malformed JSON manually and rerun the exact same contract.

Worked reasoning: Repair a trailing comma. Explain why the fixed string still needs semantic validation.

Does syntax repair justify executing a newly added tool?

No. A repair may change meaning. Compare fields and retain the allowlist regardless of parse success.

Task 7: expose arithmetic with a fixture

Check mean([1,2,6]) = 3 before reading a model explanation.

Worked reasoning: A zero-mean fixture can hide a wrong denominator; [1,2,6] makes the expected result informative.

What does one passing fixture establish?

Agreement on that fixture only. Add empty, large, negative and length-bound cases before broader claims.

Task 8: hand over the evidence ZIP

Export eight predictions, eight explanations and three reflections.

Worked reasoning: Blank answers yield draft status. Filled fields mean ready for discussion, not automatically correct.

What should a partner inspect first?

Read the contract and code before running it; compare actual results with independently calculated fixtures.

Summary: extend only a declared boundary

Optional A adds median; optional B tests proposal formatting variants.

Worked reasoning: Explain one observation for each concept and one limitation. Keep the original reference unchanged.

Why are these three different questions?

Token likelihood describes generation, permission controls actions, and correctness requires task evidence. None implies the others.

Explain next-token prediction; validate structured tool proposals; retain control outside the model. Preserve the exact inputs, source, configuration, executed outputs and one limitation.
