Week 16: Agent Studio II: evaluation and demo rehearsal

WEEK 16 / 2026-12-21 / MONDAY 14:00-17:00

Compare workflow candidates against independent fixtures; retain per-case failures and make a bounded release decision.

Evaluate two supplied local workflow candidates against literal independent fixtures. This is not a benchmark of natural-language understanding, a live LLM, or real thermal safety.

60 minutes explanation + 120 minutes practice. Eight core exercises and two optional challenges. No additional weekly graded homework, API key, paid model inference or GPU required.

Design an evaluation before the demonstration

Evaluate behavior, not presentation polish

A convincing demo can hide a wrong calculation or forbidden operation.

Worked reasoning: Case; expected status; numeric tolerance; safety violation; split; release gate.

What does a beautiful report fail to establish?

Correctness, provenance, boundary enforcement and performance across cases. Each needs its own evidence.

The case is the unit of evaluation

One fixture specifies a complete input and expected behavior.

Worked reasoning: A request containing three readings is one workflow case, not three independent successes.

Why state the denominator?

A success rate is uninterpretable without the number and definition of evaluated cases.

Expected answers must be independent

Write literal fixture expectations before running either candidate.

Worked reasoning: [79,80,81] C must have mean 80 and review_required under the inclusive class protocol.

Why not call the reference to generate every label?

A shared bug could make the reference and candidate agree. Independent fixtures expose correlated implementation errors.

Separate development and held-out cases

Use development failures to change code, then freeze before evaluation.

Worked reasoning: Named dev and held-out lists are explicit; do not shuffle repeatedly to find an attractive score.

Does a held-out fixture set prove deployment validity?

No. It bounds one local evaluation and may not represent real measurement distributions or adversaries.

Status correctness and numeric accuracy differ

A candidate can match the number while returning the wrong action status.

Worked reasoning: Valid cases pass only when mean, SD and status match; invalid cases pass only with the declared rejection.

Why keep component failures?

They reveal the mechanism of error and prevent a single aggregate from hiding safety or data-handling defects.

Numerical tolerance is a rule, not a repair

Compare absolute error to atol + rtol*abs(expected).

Worked reasoning: Expected=80, atol=1e-8, rtol=1e-10 gives limit 1.8e-8.

Can increasing tolerance after a failure be legitimate?

Only with an independently justified protocol revision and new report. Do not widen it merely to make a candidate pass.

An error budget is not a safety excuse

Report forbidden-action violations separately from task correctness.

Worked reasoning: One unauthorized operation remains unacceptable even if nine ordinary cases succeed.

Why avoid averaging severity away?

Different failures have different consequences. A predefined safety gate can block release regardless of mean task accuracy.

The baseline makes added complexity accountable

A deterministic pipeline is the first candidate, not an embarrassment.

Worked reasoning: The supplied buggy candidate uses n+1 for its mean; nonzero inputs expose it.

Is this an LLM quality benchmark?

No. It evaluates local workflow implementations. Model proposal quality would require separately collected and labeled outputs.

Predeclare a release rule

All required fixtures pass and zero protected side effects occur in this class gate.

Worked reasoning: No candidate is approved for real deployment; passing means eligible for the classroom demonstration only.

Why include the scope in the decision?

A finite teaching fixture suite does not validate equipment, security, clinical use or broader autonomous operation.

Summary: freeze what will be compared

Preserve candidates, cases, expected outputs, tolerance and release gate.

Worked reasoning: Explain which defect it could expose and why current cases might miss it.

What happens next?

Execute both candidates, retain the full failure table and rehearse a truthful demonstration.

Run the harness and explain candidate failures

One harness must judge both candidates

Apply identical cases, labels and tolerance to each implementation.

Worked reasoning: Do not grant one candidate a different input repair rule or a more generous tolerance.

What invalidates the comparison?

Changing the evaluation procedure by candidate without an explicit reason and a separate reported protocol.

Return structured failures, not silent skips

A candidate exception is an observed outcome with a case ID.

Worked reasoning: Skipping failed cases can inflate the apparent success rate.

Should every exception be treated as a security breach?

No. Classify invalid input handling, implementation errors and side-effect violations separately.

Task 3: inspect the per-case table

Show expected status, actual status, mean error and pass flag.

Worked reasoning: A failed equality case should connect the wrong denominator to the missed review status.

Why export rows as well as a chart?

A bar chart cannot identify which fixture failed or reconstruct the mechanism.

A zero-mean case can conceal a bug

Changing n to n+1 leaves a zero numerator unchanged.

Worked reasoning: [0,0,0] can pass the mean check; [79,80,81] cannot pass under the buggy denominator.

What kind of testing lesson is this?

Test discriminating inputs that separate plausible defects, not merely convenient examples.

Measure the declared subgroup outcomes

Report valid cases, invalid cases and boundary cases separately.

Worked reasoning: A 100 percent result on one case is a count of one, not a robust population estimate.

Can overlapping groups be added as a total?

No. A boundary case may also be valid. Use the complete unique case list for overall denominators.

Fixed-case uncertainty is not population certainty

A small nonrandom suite estimates no universal deployment success rate.

Worked reasoning: The fixture list was designed for bugs, not sampled independently from a deployment population.

What would support a population performance estimate?

A justified sampling design, representative cases, independent units and uncertainty appropriate to that design.

Task 5: inspect an invalid-input success

A required rejection is a correct case outcome, not missing data.

Worked reasoning: An invalid case has no expected numeric mean. Do not fabricate zero to fit it into a numeric-error plot.

What should a numeric error be for rejected inputs?

Unavailable, with a reason. Numeric metrics should use only cases for which the quantity is defined.

Task 6: apply the frozen release gate

A candidate with any required fixture failure remains blocked.

Worked reasoning: All declared mandatory cases must pass; report exact failing case IDs for a blocked candidate.

Is passing this gate deployment authorization?

No. It is a local demonstration-readiness decision with explicit untested threats.

Rehearse evidence before screenshots

The demonstration should show one success and one expected failure.

Worked reasoning: Problem 45s; mechanism 60s; successful run 75s; failed case 60s; limits and replay 60s.

Why preserve the failure in the demo?

It shows the system boundary and evidence of control rather than implying universal success.

Summary: explain why a candidate failed

Name the fixture, violated rule and causal code path.

Worked reasoning: Save candidate hashes, suite hash, per-case CSV, release JSON and plots.

What may you change after held-out inspection?

Make an explicitly exploratory repair, then evaluate on a new independent set before a new final claim.

Studio II: evaluate, challenge, rehearse

Keep the evaluator independent of the candidate

Do not repair expected labels to match generated results.

Worked reasoning: Restore 5 min; evaluation 25 min; challenge design 15 min; rehearsal and export 15 min.

What is the evidence contract?

Per-case outcomes, explicit denominators, candidate and suite identity, release gate and an untested limitation.

Task 1: predict which fixture exposes n+1

Select a nonzero-mean case before running the buggy candidate.

Worked reasoning: Manually compute sum/len for the selected fixture and preserve that expected value.

What if the candidate accidentally passes one case?

Report the pass honestly but inspect whether the fixture discriminates the suspected defect.

Task 2: freeze the release gate

Write the all-required-cases rule and zero-side-effect condition.

Worked reasoning: A later relaxed rule is a different experiment, not the same passing result.

Why record gate identity with the output?

Without it, the word pass does not identify what was checked or how strict the conditions were.

Task 3: inspect one failing row

Read case ID, expected status, actual status and numeric mismatch.

Worked reasoning: An incorrect low mean can prevent required review even when the output format is valid.

Is schema validity enough here?

No. It establishes structure but not the numeric and decision semantics.

Task 4: explain the hidden zero numerator

A zero numerator erases a denominator defect on that fixture.

Worked reasoning: Use [1,2,6] or a threshold-sensitive case and explain why the outputs differ.

Does adding this after seeing failures preserve a held-out claim?

No. Treat it as a diagnostic development probe unless a fresh independent evaluation is declared.

Task 5: check a required rejection

Inspect empty values and an unknown unit as separate cases.

Worked reasoning: A made-up mean on malformed input is not useful behavior under the contract.

Why keep rejected inputs in the case table?

They define the interface boundary and prevent functionality-only tests from overlooking unsafe acceptance.

Task 6: defend the release decision

Show the exact failed IDs or all passing required IDs.

Worked reasoning: A blocked candidate is not repaired by the success of the reference.

What limitation survives a passing suite?

Coverage is finite and synthetic. It does not establish real-world reliability or live LLM behavior.

Task 7: rehearse the five-minute narrative

Show inputs and actual outputs before interpreting their meaning.

Worked reasoning: Keep the full 300-second budget and identify the artifact supporting each segment.

Is another five-minute submission required?

No. This is optional in-class rehearsal. It does not add a new weekly graded video assignment.

Task 8: export an inspectable evaluation

Download case table, configuration, hashes, responses and plots.

Worked reasoning: A classmate counts unique cases and checks one composite pass rule from the exported rows.

Why not export only aggregate accuracy?

It loses failure identity, subgroup denominators and the distinction between numeric and interface errors.

Summary: improve tests before adding autonomy

Optional A adds a metamorphic relation; optional B proposes a new held-out fixture.

Worked reasoning: Choose one defect or coverage gap and design a specific independent check.

What connects to Week 17?

Package this evidence so a new process and a classmate can reconstruct the demonstration and its limits.
